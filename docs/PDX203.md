# Sony Xperia 1 II (pdx203) port

State on 2026-10-21: **the phone boots to the iOS lock screen** with
`cpus=8`. The shim draws on the command mode panel (autorefresh), the UFS
3.0 host works, all eight cores run, the keys read the PM8150, the root
image built with the README recipe works unchanged. The first boot of a
fresh root image needs the cores: on one A55 the LaunchServices reseed
(`lsd`) kept SpringBoard waiting for over 20 minutes, on eight it finishes
in minutes. Touch works (Samsung sec_ts over the shared GENI engine, patches 0085
to 0087), so the phone can be unlocked and used. USB device mode works
(patches 0087 to 0101, high speed only): the phone shows up as the CDC-ECM
device, the USB Ethernet link comes up and the kernel console streams to
the host over UDP (`tools/sweet-usbnet.sh`). Sony's bootloader has no
`fastboot boot`, the shim is flashed to `boot_a` (slot b is blocked by
Lineage's vbmeta, and `fastboot` 37 refuses to flash a disabled vbmeta).
Reading the persistent log works from the Lineage recovery over adb, after
killing `gvfs-gphoto2-volume-monitor` on the host, which otherwise claims
the phone's USB interface.

The Xperia 1 II is `pdx203`, Qualcomm SM8250 (Snapdragon 865, "kona"),
8 GB RAM, UFS 3.0, a 6.5" 1644x3840 OLED. The bootloader is unlocked and
supports `fastboot boot`. The facts below come from the stock `boot.img` DTB
(`kona.dtb` + the pdx203 overlay) and Sony's published kernel source
(`arch/arm64/boot/dts/somc/kona-edo-*`, `techpack/display`), not from a
live FDT: the phone has not been read with the shim yet.

## What is different from sweet

| Area | sweet (SM7150) | pdx203 (SM8250) | Verified on phone |
| --- | --- | --- | --- |
| Cores | 6x A55 + 2x A76, MPIDR Aff1 = core | 4x A55 (0x000-0x300), 3x A77 (0x400-0x600), 1x A77 prime (0x700), same MPIDR scheme | no |
| RAM | upper bank `0x1_00000000` + `0xfcc00000` | same range assumed: the boot.img DTB has no memory node, every fixed kona carve-out is in the low bank and the phone has 8 GB | no |
| GICv3 | GICD `0x17a00000`, GICR `0x17a60000` | same | no |
| Timer | 19.2 MHz, virtual timer INTID 19 (Qualcomm PPI 3) | 19.2 MHz, INTID 27 (PPI 11, the usual numbering) | no |
| UFS | `ufshc@1d84000`, UFSHCI 2.1 | same address, UFS 3.0 host; userdata is on LUN 0 (`sda`, 91 partitions) | no |
| Splash framebuffer | `0x9c000000`, 1080x2400, video mode panel | `0x9c000000` (`cont_splash_region`, 0x2300000 long), 1096x2560 (the panel's default timing; 4K is a second timing), **command mode** panel with TE | no |
| Display refresh | panel scans the buffer out by itself | the MDP only sends a frame when started. The shim turns on pingpong autorefresh (`shim/display.c`), after which the panel refreshes from RAM on every TE pulse | no |
| Reset to fastboot | IMEM `0x146aa65c` | IMEM `0x146bf65c` (`qcom,msm-imem@146bf000`), PS_HOLD `0xc264000` | no |
| Keys | PON (PM6150): power, RESIN = volume down; PM6150L GPIO2 (SID 4) = volume up | PON (PM8150, SID 0): power, RESIN = volume up; PM8150 GPIO1 (PPID 0x0c0, base 0xc000, active low) = volume down. Camera keys (PM8150B GPIO1/2) unused | no |
| Touch | Goodix GT9896, GENI I2C SE7 | Samsung `sec_ts` at I2C 0x48 on `qupv3_se13` (`0xa94000`), IRQ TLMM 39, reset TLMM 38, rails ldoc1/ldoc10 (`sects` protocol in `bsd/dev/sweet_touch.c`, wiring from `/sweet-touch`) | yes |
| USB live log | DWC3 `0xa600000` + QUSB2 PHY `0x88e2000` | DWC3 at the same address, SNPS femto HS PHY `0x88e3000` (patch 0089), high speed only (0094, the QMP SS PHY init hangs the core), usb0 behind the apps SMMU `0x15000000` stream 0, which gets an identity context bank (0100) because TrustZone turns S2CR bypass into a fault | yes |
| boot.img header | v2, ramdisk `0x1000000`, tags `0x100` | v2, kernel `0x8000`, ramdisk `0x2000000`, tags `0x1e00000`, dtb `0x1f00000`, page 4096 | yes (the Android port boots with it) |

Everything else (PSCI through `smc`, 16K pages, GIC Group 1 timer, the
SPMI arbiter v5 layout at `0xc440000` / `0xe600000` / `0xc40a000`) is the
same silicon generation and is used unchanged.

## How the board is selected

The sweet-specific numbers were moved out of the sources into one place per
layer, so a board is a set of three small files:

| Layer | sweet | pdx203 |
| --- | --- | --- |
| Device tree generator | `tools/boards/sweet.py` | `tools/boards/pdx203.py`, `tools/mkadt.py --board pdx203` |
| Boot shim | `shim/boards/sweet.h` + `sweet.sh` | `shim/boards/pdx203.h` + `pdx203.sh`, `BOARD=pdx203 shim/build.sh` |
| Kernel | one kernel binary for both | reads the framebuffer from `boot_args` (patch 0082) and the key wiring from the ADT node `/sweet-keys` (0083) |

Kernel patches 0082 to 0084 are generic, the sweet build is unchanged by
them. The drivers that only know sweet's hardware (touch, touch rail, USB)
start only when the ADT has their node (`/sweet-touch`, `/sweet-usb`), which
`mkadt.py` emits for sweet only. The kernel matches `sony,pdx203` and
`qcom,kryo585` in the ADT next to the sweet names.

## Build

Kernel, on the fork's GitHub Actions (the workflow runs on the `pdx203`
branch, no board input needed):

```sh
gh workflow run xnu.yml -R chardidathing/ios-sweet --ref pdx203
gh run download RUN_ID -R chardidathing/ios-sweet -n xnu-kernel -D xnu/out
```

Shim and payload (clang + lld are enough, `aarch64-linux-gnu-gcc` is used
when installed). The shim needs the stock boot DTB at `dtb/pdx203/dtb`
(`tools/unpack_bootv2.py` on the stock or the Android-port `boot.img`, it
is the concatenated kona dtb set that ABL picks the SoC revision from):

```sh
python3 tools/mkadt.py shim/out/pdx203.adt --board pdx203
python3 tools/mkpayload.py xnu/out/kernel.development.sweet shim/out/pdx203.adt shim/out/pdx203-payload.bin \
    --cmdline 'debug=0xc serial=3 cpus=1 keepsyms=1 -enable_kprintf_spam -noprogress rd=ufsroot0 unentitled_ios_sim_launch=1 ignition_level=1 wdt_test=no_user_checkin ufsrw=1 rootrw=1 launchd_unsecure_cache=1 wdt=-1 sweetfb_hz=30'
BOARD=pdx203 shim/build.sh ../shim/out/pdx203-payload.bin   # -> shim/out/pdx203/shim-boot.img
BOARD=pdx203 shim/build.sh                                   # no payload: diagnostics only
```

`cpus=1` for the first boots, `cpus=8` once the kernel is stable. Touch
starts when the ADT has `/sweet-touch`, USB when it has `/sweet-usb` and the
boot-args say `sweetusb=2 sweetusbhs=1` (high speed only, the pacing knob
`sweetusbpace=N` adds N ms between the bring-up steps when debugging).
`sweetfb_noconsole=1` is left out so the kernel log stays on the screen.

The host side of the live log is `tools/sweet-usbnet.sh LOGFILE` (needs
sudo for the address, listens with socat, ncat, nc or python3, whichever
exists). The kernel only streams what it logs after the link is up, so a
quiet phone gives an empty file until something happens (a tap, a key).

## Test plan

Take it in stages, each one answers one question. Reading the persistent
log from recovery (`tools/sweet-log-pull.sh`) works the same way here once
the kernel's UFS driver runs: it is the last 4 MiB of `userdata`.

1. **Shim alone** (`BOARD=pdx203 shim/build.sh`, no payload):
   `fastboot boot shim/out/pdx203/shim-boot.img`. Expected: a red screen with
   white text, the `DISP` lines first. They show the pingpong autorefresh
   register before and after, the tearcheck enable bit and CTL_TOP of CTL0.
   Then the UFS probe (version, capabilities, a `TUR`, `READ CAPACITY`, the
   GPT and the big partitions on LUN 0 with their filesystem type), and a
   reboot after about 3 minutes.
   - Screen stays on the Sony logo or black: the display is the problem, not
     the shim. Sony's bootloader may not initialise the panel on
     `fastboot boot` (its fastboot mode is dark with a blue LED). The way
     around is a normal boot with the shim in `boot_a`
     (`fastboot flash boot_a shim-boot.img`, which replaces the Android
     boot image, restore it from the backup afterwards). If the Sony logo
     stays but nothing is drawn over it, autorefresh did not take and the
     MDP needs a CTL_START per frame instead (`shim/display.c`).
   - Text is skewed or wraps wrongly: the stride is not 1096 x 4, or the
     splash timing is not 1096x2560. Adjust `FB_W`/`FB_H`/`FB_STRIDE` in
     `shim/boards/pdx203.h` and `tools/boards/pdx203.py`.
   - Phone resets immediately: the MDP registers are not accessible from EL1
     (XPU) or `0x9c000000` is not the framebuffer.
2. **Kernel to the UFS driver** (payload with `cpus=1`): the shim prints
   `INITRD`, `PHYS`, `JUMP`, then the white band and the early marks at the
   bottom of the screen, then the kernel log. Target: `SWEET UFS: "userdata"
   on LUN 0`. If the phone resets before the first mark, the RAM range is
   probably wrong (`PHYS_BASE`/`MEM_SIZE` in `tools/boards/pdx203.py`).
3. **iOS root**: build the root image exactly as in the README (needs the
   iPhone X 16.7.16 IPSW, `apfs-fuse`, `hfsprogs`, sudo) and flash it to
   `userdata` (erases Android's data). Same boot-args, expect the Apple logo
   and the lock screen after a few minutes. The 1125x2436 iPhone X canvas is
   shown centered on the 1096x2560 panel (62 black rows top and bottom, 14
   columns cut off left and right), `sweetfb_native=1` shows the native size.
4. **Keys**: power and the volume keys through `/sweet-keys`
   (`sweetkeys=0` disables). `SWEET KEYS:` lines in the log show the raw
   PON and GPIO status bytes.

Then `cpus=8`, touch and USB, all done (`SWEET TOUCH: sects` and
`SWEET USB:` lines in the log, the phone on the host as `1209:0001`).

## Assumptions to verify

- The RAM range `0x1_00000000` + `0xfcc00000`. Pull `/sys/firmware/fdt` from
  recovery or Android and check the memory node and `reserved-memory`.
- The splash framebuffer: that ABL leaves one at `0x9c000000` on
  `fastboot boot`, at 1096x2560, stride 4384, a8r8g8b8.
- Autorefresh: that ABL's pipeline (CTL0, pingpong 0, DSI0 command mode)
  keeps running with `PP_AUTOREFRESH_CONFIG = BIT(31) | 1`, and that the
  tearcheck block is already enabled (otherwise `display.c` programs it with
  the Linux defaults, vsync counter 123).
- The UFS host: UFSHCI 3.0 on kona, the sweet driver was written against 2.1.
  The shim probe prints the version register first.
- MPIDR Aff1 = core for the A77s, and PSCI CPU_ON for all eight (the shim's
  SMP test, `test_smp` in `shim.c`, can confirm this but is not run by
  default).
- Where ABL loads the Image and the ramdisk (`0x80080000` and the ramdisk
  offset): the shim is position independent, the payload only has to stay
  clear of the kernel's RAM, which the loader checks.
